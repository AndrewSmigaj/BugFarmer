## §P — Persistence

**1. The plan contradicts itself: the WORLD-STATE ledger still routes fields to the multi-record model the storage section deletes. VERDICT: REAL FLAW (spec-level).**
Ledger items 1, 2, 3, 5 say "→ `:meta`" and item 8 says "NEW per-chunk `ChunkSave.Gnaw` … filtered by chunk like every sidecar" — while the storage-model paragraph deletes the meta record, per-chunk records, and `ChunkSave` entirely in favor of `WorldSave{…}` (plan lines 124–157 vs 162–177, "meta record" is explicitly in the before-list of the concept count at line 179). This is exactly round-3 residue carried along: an implementer following item 8 literally builds a per-chunk map into a record type the same document says no longer exists. Minimal fix: rewrite items 1–8 against `WorldSave` field names before A0 starts; the ledger and the storage model must be one artifact.

**2. Eager apply is under-specified where it actually bites: the init scans. VERDICT: REAL FLAW (missing spec), mechanism itself sound.**
`handleChunkSubscribe` only runs `applyChunkSave` + the five init scans when the chunk is NOT already in `state.Chunks` (handlers_world.go:23–45). If MatchInit force-loads touched chunks into `state.Chunks` without running the init scans there, subscription skips them forever — any tree/flower/nest in a touched chunk that isn't in the save (e.g. a zone-file update adding occupants) never gets a state. The plan never says the scans move to eager-load. I verified the guards the design depends on ARE all skip-if-present: nests (nests.go:91–93), stations (handlers_farming.go:1002), host plants (:1376), forage pools (:1444), fruit trees (:1512) — and tree init randomness is posHash/position-keyed, load-order-independent (state.go:34–41, handlers_farming.go:1534–1538), so eager loading is safe *if* specified. But then note: "deletes the ENTIRE two-phase restore-ordering subtlety" (line 171) is an overclaim — the restore-before-init-scan ordering constraint survives, relocated into MatchInit. Fix: A0 spec must say "eager load = LoadChunk → apply edits → run the five init scans, per touched chunk, in that order," and the claim should be downgraded to "the ordering collapses into one function."

**3. The ONE-document premise itself checks out. VERDICT: NON-ISSUE (verified, not taken on faith).**
No storage size constraint exists in this deployment: `local.yml` has only *socket* limits (the 8MB `max_message_size_bytes`, line 11); server-side `StorageWrite` goes straight to Postgres. No runtime code reads an individual chunk record: `LoadChunkSaves`/`LoadZoneMeta`/`ZoneStateCollection` appear only inside zone_persist.go, and `chunkForCollision` overlays from the in-memory `ZoneChunkCache` (state.go:756–767), not storage. Memory at init is bounded by 64 chunks/zone. One caveat the design already implies but must honor: "touched chunks" must include every chunk with a `CellEdit`, or `chunkForCollision`/`BlocksBugsCells` loses its delta overlay once `ZoneChunkCache` is deleted.

**4. "Clear ONLY DefendTargetID — the single session-scoped field" is false twice. VERDICT: REAL FLAW (claim-level; behavior self-heals).**
(a) `WindupTargetID` is the same class — a player reference stored on the swarm (centipede.go:134). (b) Neither is a *session* id: both hold userIDs (recallNestDefenders takes the attacker userID, nests.go:641–658; the defend entry stores `nearestPlayer`'s `state.Players` key, predation.go:131–133), which are stable across reconnects. Both self-heal when the player is absent (defend exit predation.go:140–152; windup abort centipede.go:157–161). Minimal fix: the classification table needs a "player-ref" field class handled uniformly — either clear both or (more honest under "time continues," since userIDs are stable) clear neither and rely on the verified self-heal paths.

**5. Full-fidelity restore freezes CONFIG-derived fields inside SwarmState. VERDICT: REAL FLAW.**
`Radius` and `WanderRad` are copied from species data at mint (handlers_bugs.go:105–107) and never re-read. Byte-faithful restore of the whole struct means a species.json rebalance (swarm_radius, wander_radius) silently doesn't apply to any persisted swarm — a CONFIG value smuggled through WORLD-STATE, violating the design's own three-class principle at the *field* level while the enforcement test only checks the *struct* level. Minimal fix: on restore, refresh config-derived fields from the live species def (one loop), and note in `persist_classes.go` that classification is per-field even inside persisted structs. Related nit: `entities.SwarmState` has no json tags — the save format couples to Go field names; a rename silently orphans saved data. Tag the struct in A0.

**6. Mid-phase restore + first-client bootstrap: survives the attack. VERDICT: NON-ISSUE (with two notes).**
`buildSwarmSeedBaseline` carries Phase/NextBugID/RemovedIDs and hydrates the live leg from the influence log (match.go:2736–2763) — post-restart that log is empty, so restored swarms with persisted `HasTarget=true` march server-side while every client holds the centre until the next think leg (≤ ~5s: wander 30+rand(21) ticks, hunt re-aim 10+rand(6)). All clients agree with each other; the next leg's origin re-anchors them; the client consumes Phase only as metadata (SwarmManager.cs:940). Notes: (i) a restored mid-gnaw centipede whose fence chunk isn't eager-loaded aborts via `occupantDefAt` nil-chunk → `endGnaw(false)` (centipede.go:344–349, 393–398) — damage is retained, no strand, but "time continues" quietly becomes "the gnaw stops"; (ii) tick anchors (`NextThinkTick`, `FeedUntilTick`, `SurgeCooldownUntil`…) are all valid under the resumed clock because MatchLoop pauses TickCount when empty (match.go:810–821) — verified no consumer of the Nakama `tick` param in sim paths.

**7. Migration is the least-designed corner. VERDICT: REAL FLAW (small, but the exact class of skew bug this design brags about killing).**
The plan (lines 175–177) never states: (a) precedence when BOTH the new doc and legacy records exist — if the loader ever prefers legacy, a later boot re-imports stale state over newer doc saves; (b) when legacy records get *deleted* (if never, a rollback resurrects ancient state and garbage accrues); (c) any generation guard on the doc — the async empty-transition save (match.go:745–747) can complete *after* a newer terminate save (match.go:1594) and roll the whole zone back a generation. Also, "strictly MORE crash-safe: no index-vs-records skew window" attacks a strawman: today's save is already ONE batched `StorageWrite` call (zone_persist.go:456–470). The real win is cross-*save* interleaving (one doc can only be wholly stale, never mixed-generation) — say that instead. Minimal fix: new-doc-wins precedence; delete legacy records on first successful new-doc write; stamp `WorldSave.Tick` and refuse to overwrite a newer doc with an older snapshot.

**8. The "complete" census isn't quite complete — but the enforcement test is the right answer. VERDICT: DEFENSIBLE-BUT-NOTE.**
Unmentioned fields: `LastMergeCheck` (state.go:117), `LastZoneSaveTick` (zero at boot + resumed clock → one spurious autosave on the first occupied tick, match.go:836–841 — set it to TickCount at restore), `CreatedAt` (re-minted `time.Now()` every MatchInit, state.go:381). The reflection test will force all of these — good; the plan's "complete field-by-field inventory" wording just overstates the written artifact.

## §C — Condition/Subdual

**10. Two thresholds create a player-visible incoherence band. VERDICT: REAL FLAW (design smell).**
Global CALM≥30 (behavior) + per-species `condition_threshold` (catch, bee=40) means a decaying bee spends 30→40 *placid but "too agitated — calm it first."* The schema already has the per-species knob; the centipede (trap_only, no catch) still needs a behavior floor, so make `condition_threshold` mean "subdued at/above this" for BOTH behavior and catch, with the const as the default when absent. One knob, coherent reads, and the catch gate at match.go:2431–2449 (location verified — the plan's :2432–2448 is accurate) compares against the same number the funnels use.

**11. The v1 numbers contradict the stated fantasy by an order of magnitude. VERDICT: REAL FLAW.**
"A strong calm lasts ~30s" is only true at fill≈90 ((90−30)/2). The plan's own table: centipede fill 35 → **2.5 seconds** of calm; wasp 45 → 7.5s; bee 60 → 15s. The GDD's flagship play — "Far too big for any net: subduing comes with the smoker" (game_design.md:425–426) / walk past the centipede — is unplayable in a 2.5s window against a per-tick re-trigger at range 5.0 (centipede.go:128–142). Also unspecified: does applying an effect SET, ADD, or MAX the meter (spam-to-100 vs fixed windows)? And species.json's explicit `condition_decay: 0` (fly/butterfly) is ambiguous against "default 2/sec" — 0 can't mean "no decay" if 0 means "default." Fix the arithmetic (fills ≥70 for the tools, or per-species decay), define stacking, and define zero-vs-absent before A1.

**12. Mid-gnaw is the missing calm case. VERDICT: REAL FLAW (missing case).**
The plan suppresses windup start, aborts windup/surge, and blocks gnaw *start* — but a centipede already in `ActionState "gnaw"` keeps chewing (up to `centGnawTimeout` 900 ticks = 90s, centipede.go:55) straight through any calm you apply. The calm swarm continues its most destructive act while "subdued." Fix: one check at the top of `processGnaw` → `endGnaw(state, swarm, false)` (no cooldown — the world didn't change, the bug did).

Mid-surge: `case "surge":` at :81 — but `startRecover` requires an away-from point (:275–282); the calm-abort must pick one (windup target's position if connected, else current pos + heading). **14. `condition_tools` default-40 guts the schema's opt-in meaning. VERDICT: REAL FLAW (simplification).**
The map exists precisely to say *which* effects work on *which* species; a code default makes every present and future species calmable by every effect unless someone remembers to opt out — the blanket leaks forward (boss species, future effects × `effect_power`). And the cost of honesty is zero: the plan's own species table (lines 265–271) already enumerates all six species — write the 40s into data, drop the code default, and "no key = this effect does nothing to this species" (the toast already exists for feedback). "Vast majority calmable" survives untouched because the majority *is* explicitly listed.

**15. The new consumable OpCode is not the minimal verb. VERDICT: REAL FLAW (excess mechanism).**
`ToolUse` (OpCode 7) already is "apply the equipped item at a grid cell": same message shape (`grid_x/grid_y`, ToolUseController.cs:89–96), the server derives the item from `EquippedTool`, which is set for ANY item id via OpCodeEquipTool (match.go:925 — no tool-type filter), and `handleSmoker` already lives inside the `handleToolUse` switch (handlers_farming.go:63–75). Routing calm_spray = one `case "consumable":` (or category check) in that switch + one case in PlayerInputRouter's left-click switch (PlayerInputRouter.cs:96–131, where today it falls through to grab/break — the plan's claim verified) + a stack decrement + SlotUpdate (both exist). That also gives you `validateToolCooldown` for free — which a fresh OpCode would have to re-plumb. A new OpCode + new message + new client controller path buys nothing; the plan even routes the *smoker* through OpCode 7, so §C would ship the same effect application behind two different network verbs. Demand: one verb, OpCode 7.

**16. SmokedUntilTick + ConditionValue two-stamp: survives the attack. VERDICT: DEFENSIBLE-BUT-NOTE.**
The away-forager case is real, not hypothetical: the recall reads only the nest stamp (nests.go:647–649), and residents are out foraging most of the time — smoking the *hive entrance* while the bees are afield is the core beekeeping loop (handlers_hive.go:44–47 fires the recall on every harvest). Neither field alone covers the space: the meter alone can't express hive-local lingering smoke without action-at-a-distance (calming a swarm 30 cells away), and the stamp alone can't calm nestless species (centipede — the GDD's flagship target). Two fields, two honest meanings — the minimal set. Demand only: write the precedence rule once ("defend/recall suppressed while `resident calm OR nest smoked`") and apply it at all three nest entries (predation.go:127 passive entry, nests.go:647 recall, and the exit hysteresis) so nobody later "simplifies" one of the three differently.

## Overall judgment

**§P is a genuine root fix wearing an unreconciled spec.** Resumed clock + full-fidelity swarms + the reflection-enforced classification table attack the actual root cause (lossy restore + clamp/relink patches), and its two latent-bug finds check out — this is not another layer. But the plan document itself is internally inconsistent (finding 1), under-specifies the one mechanism that can silently rot (finding 2), and hand-waves migration (finding 7). Built as written, an implementer could faithfully produce a hybrid of the round-2 and round-3 designs.

**§C is the right architecture with wrong numbers and one gratuitous mechanism.** Implementing the dead schema stub instead of a bee-only gadget is the root fix, and the two-stamp smoke model survives adversarial pressure. But the threshold split (10), the 2.5-second flagship calm (11), the mid-gnaw hole (12), the default-40 blanket (14), and the redundant OpCode (15) are each small accretions of exactly the hack-on-hack character the owner is angry about — cheap to fix now, expensive to excavate later.

**Top 3 changes demanded before implementation:**
1. **Rewrite §P's ledger against the ONE-document model and spec the eager-load sequence** (LoadChunk → apply → the five init scans, per touched chunk; new-doc-wins migration precedence + legacy deletion + a doc generation stamp). Findings 1, 2, 7.
2. **Collapse §C to one per-species subdued-threshold and fix the fill/decay arithmetic** (define set-vs-add, make the centipede window match "walk past it", close the mid-gnaw hole). Findings 10, 11, 12.
3. **Delete the two blanket mechanisms:** the code-side `condition_tools` default (explicit data for the six species instead) and the new consumable OpCode (route through ToolUse/OpCode 7). Findings 14, 15.
