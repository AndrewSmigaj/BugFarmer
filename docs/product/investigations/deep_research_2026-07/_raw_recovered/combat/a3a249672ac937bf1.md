**Engine-feature note (DOTween vs AnimationCurve vs PrimeTween):** AnimationCurve gives designers Inspector tuning (`SetEase(AnimationCurve)`), costs a binary-search `Evaluate` per frame (negligible) but curves don't port between projects. DOTween sequences are convenient but **allocate/GC**; **PrimeTween** (github KyryloKuzyk) is allocation-free and does the same `Sequence` API. For a ~0.2s swing that fires constantly, prefer **pure easing math or a spring** (zero alloc) over DOTween.

## THE PROCEDURAL GAME-FEEL TOOLKIT (phases, curves, numbers)

### The 4-phase motion profile (per swing)
Drive one pivot **angle** (and a scale for squash) through these phases. Total "active" duration ~0.14–0.22s; settle overlaps/extends after.

| Phase | % of active dur | Angle behavior | Curve | Why (source) |
|---|---|---|---|---|
| **1. Anticipation (wind-up)** | **10–20%** (keep SHORT) | rotate *backward* opposite the swing by ~15–30% of swing arc | **EaseOutQuad/Back** (moves away, decelerates) | Sells weight, but player-action anticipation = input lag, so minimal (Cooper) |
| **2. Action (strike)** | **25–40%** | rotate fast to contact angle | **EaseInCubic** (or expo) = "fast-in" | Fast-in for responsiveness/power (Cooper "fast-in, slow-out"; Febucci cubic=weight) |
| **3. Contact / impact** | ~1 frame + **40–80ms hold** | freeze at contact angle (hitstop), fire trauma-shake + squash | hold + trauma² decay | Impact frames held longer read as force (Wayline: 150–200ms for heavy; hitstop) |
| **4. Follow-through + settle** | **40–55%** | overshoot slightly past, then settle to rest | **EaseOutBack** (overshoot) → **spring** settle | Overshoot "is what sells it"; springs are interruptible (Jonasson/Purho; springs articles) |

**Practical total durations:** snappy hoe/shovel tap ≈ **0.22–0.30s** total (windup ~0.03s, strike ~0.07s, hold ~0.05s, settle ~0.10–0.15s). Heavy axe/pickaxe ≈ **0.35–0.5s** (longer windup ~0.06s + longer settle). Rule: heavier tool = more anticipation + more follow-through, faster tool = compress phase 1 toward zero.

### The overshoot / back-ease math (verified from code)
```
s = 1.70158            // → ~10% overshoot; raise s for a punchier recoil
EaseInBack(t)  = t*t*((s+1)*t - s)
EaseOutBack(t) = 1 - EaseInBack(1-t)      // overshoots PAST target then returns — use for phase 4
EaseInOutBack: use s*1.525
```
Elastic (only for loot/celebration, **skip for tool swings** — too oscillatory/slow for 0.2s):
```
p = 0.3;  EaseOutElastic(t) = pow(2,-10t)*sin((t - p/4)*2π/p) + 1
```

### The spring settle (recommended over back-ease for the recoil, because interruptible)
Allen Chou's **stable semi-implicit** update (safe at any framerate):
```
Δ  = (1 + 2hζω) + h²ω²
x' = ((1+2hζω)*x + h*v + h²ω²*xt) / Δ
v' = (v + hω²*(xt - x)) / Δ
```
Designer params: `ω = 2π·f` (f in Hz), `ζ = ln(pₐ)/(−ω·tₐ)`.
- **Snappy tool recoil:** f ≈ **3–5 Hz**, ζ ≈ **0.35–0.5** → one visible overshoot then settles in ~0.15–0.25s.
- **No bounce (critical):** ζ = 1.
- **"Velocity nudge"** = on contact, add an impulse to `v` (don't move `xt`) → the tool kicks and springs back. This is the cleanest recoil.

### Squash & stretch on the single sprite (non-uniform localScale, volume-preserving)
Game engines often skip bone-scale, but you scale the whole sprite transform (Cooper; springs articles):
- **Wind-up/strike:** stretch along the swing axis → `localScale ≈ (1.10 length, 0.90 width)`.
- **Contact:** squash → `localScale ≈ (0.85 length, 1.15 width)` for the ~50ms hold, then spring back to (1,1).
- Drive scale with the **same spring** (f≈4–6Hz, ζ≈0.4) so squash overshoots into a slight stretch and settles — "that overshoot is what sells it" (Jonasson/Purho). Keep length×width ≈ constant to preserve volume.

### Impact beat (fire at contact, not the swing)
- **Hitstop:** freeze the swing 40–80ms on contact.
- **Trauma shake** (Eiserloh): on hit `trauma += 0.3`; each frame `trauma -= decay`; offset/angle = `maxAmt * trauma²`. Square so it eases out naturally. Apply to camera or a tiny tool jitter — not the swing curve.

### Composition without AnimationCurve (Eiserloh mixing)
If you want a single tunable curve instead of chained coroutines: build it from cheap pieces — `Mix(SmoothStart2, SmoothStop3, w)` to slide between "fast-in" and "slow-out," or `Scale(Arch2)=t²(1−t)` for a pop-and-return in one function. Cheaper than `pow()` and fully data-drivable per tool.

## WHAT TO SKIP (and why)
- **Elastic/Bounce easing for the swing** — oscillation is too long/wobbly for a 0.2s tool; reserve for loot/UI pops only (Febucci, Cooper both flag these as "celebratory").
- **DOTween Sequences for the hot path** — GC allocations firing every swing; use pure easing math or a spring (or PrimeTween if you want the Sequence API allocation-free).
- **Long anticipation on the player tool** — direct input-lag hit; if you want the *look* of anticipation, use the "squash-frame-while-already-moving" trick (Wayline/GMTK): start the tool moving immediately and let squash/stretch imply the wind-up.
- **Full 12 principles literally** — Staging and Solid Drawing/Appeal are authoring/art concerns, not procedural knobs; the load-bearing ones for us are Anticipation, Slow-in/Slow-out, Follow-through+Overlap, Squash/Stretch, Timing, Exaggeration.
