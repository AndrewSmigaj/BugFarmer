## 1. The core lesson: per-unit A* does NOT scale — move to FIELD-based movement

**[DEV — Supreme Commander 2, Elijah Emerson, *Game AI Pro* Ch.23 "Crowd Pathfinding and Steering Using Flow Field Tiles"]** (PDF fully read: gameaipro.com/GameAIPro/GameAIPro_Chapter23...)

The single most load-bearing source. Emerson was tasked with fixing SupCom2 movement. The problem he describes verbatim:

- Originally each unit moved along a **fixed, one-way A\* path**. Units collide "especially when they were moving in formation or moving into battle."
- When paths cross, the old code would **stop units and wait** for the conflict to resolve rather than repathing — because "rebuilding a path every time there is a collision turns into a compounding problem... the new path will likely lead to a second and third collision, causing the game to grind to a halt."
- To dodge this, all movement was engineered to "prefer to stay on the same path," which crippled physics, formations, AI, and hit reactions. Players had to **babysit units** ("watching and clicking, watching and clicking").

The fix: replace per-unit paths with **shared flow fields**. Key stated benefits: "agents move instantly despite path complexity" (immediate feedback), supports "obstacle avoidance, flocking, dynamic formations, crowd behavior, and support for arbitrary physics forces, all without the heavy CPU burden of repeatedly rebuilding individual paths for each agent," scaling to "hundreds to thousands of individual agents across massive maps."

## 2. Movement mechanism — the SupCom2 flow-field-tile pipeline (the detailed how)

**[DEV — same chapter]**. This is the fully-specified, shipped mechanism:

### World layout (hierarchical)
- World split into **sectors** of **10×10 grid squares**; each grid square = **1×1 meter**.
- **Portal windows** cross each sector boundary (a portal is the open span along a shared border). Sectors + portals form a coarse **portal node graph** for hierarchical pathfinding.

### Three field types (per sector tile)
1. **Cost field** — 8-bit per cell, 0–255. **255 = wall**; 1–254 = traversal cost (slopes, swamp = higher). Minimum cost 1. Optimization: a sector that is entirely clear references a single **global static "clear" cost field** of all-ones — no per-sector memory. In SupCom2, **50–70% of pathable space was "clear"** (open land, lakes, oceans). Cost data prebuilt by the editor from geometry/slope; a **blur pass** adds a cost gradient near walls so units flow smoothly down hallways / around jagged edges. Designers could hand-paint cost.
2. **Integration field** — 24-bit (16-bit integrated cost + 8-bit flags like "active wave front", "line of sight"); optionally a 32-bit float for higher quality.
3. **Flow field** — 8-bit: **4 bits index a direction lookup table** + 4 bits of flags ("pathable", "has line of sight"). This is what the steering pipeline reads.

### Path request flow (two-level)
1. **Coarse A\* over the portal node graph** (not the grid) — cheap. Produces a linked list of "next" portal nodes from source→goal.
2. **"Merging" A\*** for additional sources: subsequent units' portal-walkers prefer to **stop and point at an already-traversed portal node** to *merge* with earlier results. Effect: units selected toward one goal **share flow fields and path closer together** — coordinated group movement falls out for free.
3. Walk the portal list, submit a **flow field request per portal** — then done. "Because you've only traversed the portal node graph... you've used very little CPU."

### The Integrator (builds one flow-field tile over 1+ ticks)
Uses the **Eikonal equation** to integrate the goal wave front outward (analogy: ripples from touching still water). Steps:
1. Reset integration field, seed the initial goal wave front (a single 0-cost cell for the final goal; ten cells for a 1×10 / 10×1 portal window).
2. **Line-of-sight (LOS) pass**: near the true goal, flag cells with LOS by incrementing wavefront cost by 1 (ignoring cost-field values) until hitting cost>1. Detects **LOS corners**, then uses **Bresenham's line** to mark "Wave Front Blocked" cells bounding the visible region. Agents inside LOS **ignore the flow field entirely and steer straight at the exact goal** — avoids the diamond-shaped flow artifacts you'd get from only checking 4 neighbors.
3. **Cost integration pass**: Eikonal fill over the non-visible cells (add cheapest of up/down/left/right neighbor's cost+integrated cost). Important optimization: **stop the wavefront when it hits already-integrated results unless the difference is significant** — otherwise wavefronts bounce back and forth wastefully. (Analogy given: a path splitting around a costly "sand trap" — the cheaper branch overwrites the expensive one and back-propagates to redirect flow.)
4. **Flow field pass**: for each cell, either write the LOS flag or compare **all 8 neighbors** to pick the cheapest direction → store the direction index.

### Flow field cache (the key sharing/perf structure)
- Each flow field has a **unique ID based on the portal window it routes through**, so "work can be shared across path requests despite having different goals." (A shared hallway → one flow field reused by many paths.)
- **Reference-counted**; discarded (or timer-discarded) when unreferenced.
- Can **prebuild all flow-field permutations to disk**, building at runtime only the custom-LOS goal tiles.

### Steering on top of the field (agent layer)
- If no valid flow field yet → steer to next portal position. If in LOS → steer to exact goal. Else → follow flow field direction.
- **Blend new flow directions into a stored path-direction vector as the agent crosses grid squares** — smooths direction changes. (Note the community how-to below independently recommends bilinear interpolation of the 4 nearest cells for the same smoothing.)

### Collision & PUSH (physics layer)
- **[DEV]** Once units move freely they hit walls/each other, so SupCom2 lets **agents push each other around and slide along walls using physics**. This enabled emergent gameplay: **explosions push units back; a super-large robot pushes back a hundred tanks**; a structure that pulls units; a whirlwind unit that sucks units in and spins them until they smash. Emerson's explicit point: these physics-push scenarios "would not have been possible without the cheaper movement cost associated with using flow field tiles" — i.e. *cheap movement is what buys you a real push/physics layer.*

### Large units / multiple movement types
- Each **movement type has its own cost field & portal graph** (land tank ≠ hovercraft over lakes).
- Large units: a **"wall cushioning" pass moves walls outward**, closing gaps too small for big units and preventing visual overlap with mountains.
- Mixed selection → the game paths everyone by the **"most restrictive movement type"** first, then builds extra paths for incompatible units. (This is a big part of why a mixed army reads as coordinated — they share the restrictive path.)

### Dynamic world
- Moving sources → re-run merging A* over portals if the unit leaves its planned sectors. Moving goal → rebuild goal flow field; most tiles are already cached. Changed walls/hills/buildings → mark cost field **dirty**, rebuild affected portal-graph nodes + paths.
- **Cost stamps**: buildings "stamp" custom cost (incl. 1×1 walls), recording originals; overlapping sectors flagged dirty.
- All rebuilds run off a **priority queue with a fixed millisecond time-slice per tick** — controls when/how much rebuilding happens.

### Island fields
- Optional per-sector **island ID**; sub-divides to per-cell IDs when a sector holds >1 island. Lets you instantly reject an unreachable path (source island ≠ dest island) — that's how the SupCom2 cursor turns into a "stop sign" over unreachable terrain.

### Minimizing CPU
- **Cap the number of tiles / grid squares committed per tick.**
- Integration field memory is separate → **integration work spreads across threads.**
- Future-work list: GPU Eikonal solve, disk-streamed compressed permutations, hierarchy of sectors for arbitrarily large maps, multi-goal fields ("perfect for zombies chasing heroes").

## 3. Continuum Crowds (Treuille) — the density/velocity field model RTS flow fields descend from

**[COMMUNITY — howtorts.github.io "Continuum Crowds" and "Basic Flow Fields"]** (both fetched). This is a hobby dev's faithful walkthrough of the Treuille et al. academic approach that SupCom2 built on.

- **Basic flow field** = (a) a **Dijkstra/BFS flood-fill "integration field"** giving distance-to-destination per cell, then (b) per cell, pick the lowest-distance neighbor (8-way incl. diagonals) and store a normalized **direction vector**. Obstacles left unmarked.
- **Shared field**: many agents follow the same precomputed field — "eliminates per-unit pathfinding... dramatically reducing computational overhead compared to individual A* per agent."
- **Smoothing**: agents sample via **bilinear interpolation of the 4 nearest cells**, weighted by proximity.
- **Continuum Crowds adds two dynamic grids**: a **density grid** (agent concentration, splatted to a cell + neighbors) and a **speed/velocity grid**. Per timestep: clear grids, deposit density + density-weighted velocity, divide speed by density → average velocity per cell.
- **Cost field becomes dynamic & directional**: traversal cost rises when moving **against the local crowd velocity** (discourages counterflow) and through discomfort terrain; obstacles = infinite cost. Then an **Eikonal fill** per destination group produces the flow field.
- **Collision/congestion is emergent, not explicit**: "density fields and opposing velocity costs create implicit pressure gradients. Units avoid high-density regions and counterflow **without explicit steering behaviors.**"
- The author flags the cost: **full recompute every timestep** is heavy — which is exactly why SupCom2's tiling + caching + capped-per-tick approach exists.
- Both articles stress flow fields alone aren't enough — production needs **physics + flocking + pre-emptive collision avoidance layered on top.**

**[COMMUNITY]** search-surfaced context (not deep-fetched, lower confidence): SupCom2's flow field is explicitly "based on Continuum Crowds"; sectors are 10×10 with portals; tiling exists to reduce memory/generation time. (Consistent with the DEV chapter above.)

## 4. Flocking / steering layer — separation, alignment, cohesion (the "boids" that ride on the field)

**[COMMUNITY — ap011y0n.github.io "Group Movement", a research reimplementation]** (fetched). Craig Reynolds' 1986 Boids model, three steering forces:
- **Separation** — "pushes units apart by maintaining distance from nearby flock mates"; accumulate relative-position vectors to neighbors in collision range, invert + normalize. **This is the soft anti-overlap force** (distinct from hard physics push).
- **Cohesion** — steer toward the average position (center of mass) of nearby allies; caps force within a threshold to avoid overshoot.
- **Alignment** — steer toward neighbors' average velocity/heading (optional; makes a group move as one).
- **Architecture**: final velocity = **path-follow velocity + separation velocity + cohesion velocity**, summed. A* provides waypoints; recompute path only on a blocking entity or a new order.
- **Three radii per unit**: vision radius (cohesion neighbors), body radius (physical collision), collision range (separation trigger).
- **Pre-emptive obstacle avoidance**: zero the velocity component that would drive a unit into a wall.
- **Perf**: 100+ entities at 60 FPS, ~**0.04 ms/entity**; pathfinding causes spikes; recommends **spatial partitioning (map sectors)** + **Jump Point Search** to scale.

The **[COMMUNITY]** SC2-pathfinding search results corroborate the general SC2 stack: **constrained Delaunay triangulation navmesh** of terrain+buildings, **A\* with a funnel algorithm** accounting for unit radii, plus **boids-style separation/alignment/cohesion + local avoidance ("horizon analysis")**. Notable stated avoidance refinements: **reduce local-avoidance priority for agents that have reached their destination**, and **make agents stop when unit density around the destination is high** (prevents the endless jostle at a move-order endpoint). *Treat these SC2 specifics as community reconstruction, not Blizzard-confirmed.*

## 5. Collision & PUSH resolution — priority-based displacement

Two distinct layers, both present in real RTS:

- **Soft (steering) layer** — boids **separation** force continuously nudges overlapping units apart (§4). Local-avoidance / "horizon analysis" steers around imminent collisions before they happen. **[COMMUNITY]**
- **Hard (physics) layer** — units **physically push each other and slide along walls**; heavier/priority units displace lighter ones (SupCom2: a giant robot shoves 100 tanks; explosions knock units back). **[DEV]**
- **Priority push in SC2** — the search-surfaced characterization is that **higher-priority units shove lower-priority units aside**, and units that have reached their goal lower their avoidance priority so still-moving units can pass through/around them. **[COMMUNITY — SC2 reconstruction, medium confidence; I could not fetch a Blizzard-authored source]**. This "priority-based displacement" is what stops a stopped clump from permanently blocking a moving group.

Design takeaway: collision is resolved by **displacement (push), not by repathing**. Repathing-on-collision is exactly the compounding failure Emerson called out **[DEV]**.

## 6. Target assignment / acquisition

**[COMMUNITY — Liquipedia (SC2), Wayward Strategy, slashskill combat-system guide, via search summaries; deep-fetch of these was rate-limited]**

- **Acquisition range vs weapon range**: every combat unit has a **detection/acquisition radius**; an enemy entering it becomes a candidate. In SC2, a unit considers targets within its **Scan Range**, default **5 or weapon range, whichever is greater**. **[COMMUNITY — Liquipedia]**
- **Target lock / stickiness**: SC2 units, once a target is chosen, **keep it until it stops being valid** (dies, becomes invisible/cloaked, goes up a ramp out of sight, or leaves weapon range) *or a higher-priority target enters range*. This **stickiness prevents per-frame target flicker.** **[COMMUNITY — Liquipedia]** A hobby project ("Heresy RTS") independently arrived at the same rule: keep a focus target, only switch on death / out-of-range / higher-priority threat. **[COMMUNITY]**
- **Selection heuristics**: closest-enemy is simplest but causes **focus-fire clumping problems**; better systems use a **priority/threat value** per target type. **[COMMUNITY]**
- **Spreading fire**: SC2 gives a short **acquisition delay when switching targets**, which **naturally spreads fire** across multiple enemies instead of all units dogpiling one; combined with **overkill prevention** (stop firing at already-doomed targets). **[COMMUNITY]**
- Confidence note: these targeting specifics are community/wiki documentation of observed behavior, not a Blizzard engineering source. Directionally reliable (Liquipedia is well-maintained) but not GDC-confirmed.

## 7. StarCraft 1 "magic box" / mutalisk stacking (classic formation quirk)

**[COMMUNITY — Liquipedia Brood War, StarCraft Fandom wiki, via search]**

- SC1 keeps a selected group **in formation only while units are within a certain distance ("the magic box") of each other**; move within the box → hold formation; a member outside the box → the group collapses/stacks toward one point.
- **Mutalisk stacking exploit**: put a far-away unit (e.g. an Overlord) in the selection so it sits **outside the magic box**, forcing the mutalisks to **stack onto a single point** → they all hit one target simultaneously and can't be individually focused. Requires **constant move commands** (a stopped stack fans back out); **diagonal movement always stacks**.
- Relevance to a swarm game: formation cohesion is a **distance-thresholded behavior** — a clean, cheap rule (are my units within radius R?) that produces either tight-formation or collapse-to-point behavior. Useful, lightweight model.

## 8. What makes an RTS army read as "coordinated / intelligent"

Synthesized, each backed above:
1. **Shared paths/fields, not independent paths** — merging-A* + shared flow-field cache make units selected together funnel through the same corridors and arrive together. **[DEV]**
2. **Instant response** — field-based movement means units react the *instant* you click, even mid-path; no per-unit A* stall. **[DEV]**
3. **Move by the most-restrictive member** so a mixed group stays together rather than the fast units racing ahead. **[DEV]**
4. **Push instead of repath** on collision, with priority displacement — units flow through/around each other instead of freezing or scattering into chaotic reroutes. **[DEV push] + [COMMUNITY priority]**
5. **Boids separation/alignment/cohesion** give organic spacing + shared heading. **[COMMUNITY]**
6. **Settle-down behavior** — lower avoidance priority + "stop if destination is crowded" so an arrived group doesn't jitter forever. **[COMMUNITY, SC2]**
7. **Sticky, priority-weighted targeting with acquisition delay** — armies focus sensibly without flickering, and fire spreads instead of full-dogpiling. **[COMMUNITY]**
