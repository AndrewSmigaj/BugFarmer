## (b) Player / character-state split

Player state lives **outside** zone state entirely: `CharacterSave` in collection `"character"`, **user-owned** (`Key=charID`, `UserID=account`, `PermissionWrite:0`), written on leave and read on join (`character_persist.go:26-51`, `match.go:685-696` save; `match.go:462-484` load). Zone state (`zone_state`) is system-owned/shared. The two are fully decoupled — a character carries across zones; a zone carries its farm+bugs across restarts.

**Persists (CharacterSave, character_persist.go:26-51 / buildCharacterSave:134-159):** `Coins`, `BugSlots[20]`, `ItemSlots[40]`, `ItemSlotsUnlocked`, `Equipment[8]`, `EquippedTool`, `HP`, `MaxHP`, `Appearance`, `Name`(→Username), `IntroSeen`, `KnownRecipes`, `CharCreatedAt`(→CreatedAt), `HomeZone/HomeX/HomeY`, and logout location `LastZone/LastX/LastY`.

**PlayerState fields that DON'T persist (state.go:281-331):**
- `Position` — not saved as such; only reconstructed at join from `HomeX/Y` (bed in this zone) or `LastX/Y` (same-zone logout) or zone spawn_point (match.go:468-481). Cross-zone edge entry overrides both (match.go:490-494).
- `Facing` (284) — resets to `DirDown` (AddPlayer).
- `LastCatchTick` (298), `LastToolTick` (306), `LastDamageTick` (313) — all tick-anchored cooldowns; not saved, and would be meaningless anyway since TickCount resets.
- `PendingIntro` (321) — transient one-shot.
- `HP` (311) — **persisted-lossy**: saved, but `applyCharacterSave` clamps `HP<=0 || HP>MaxHP → MaxHP` ("log back in alive", character_persist.go:113-116). Partial HP in (0,MaxHP] survives exactly; only death→full.
- `UserID` (282) is the account id (not saved in the record body, it's the storage key).

`PlayerCells` (the influence-cell map) is separate WorldState/sync state, cleared on leave (match.go:711).

## (c) Save / restore flow, triggers, ordering, size constraints

**Record layout** (all under `ZoneStateKey(zoneID,"")` = bare `zoneID`; the `instanceID` slot reserves future private plots, zone_persist.go:33-42):
- `<zoneID>:meta` — `ZoneMeta{Version, ZoneID, LastRolloverDay, ModifiedChunks[], SavedAt}` (index of which chunk records exist; StorageList can't prefix-filter).
- `<zoneID>:swarms` — `ZoneSwarmSave{Version, ZoneID, Swarms[]SwarmSave}` (its **presence, even empty, means "restore exact population"** incl. "player caught them all", zone_persist.go:98-103).
- `<zoneID>:<cx>_<cy>` — one `ChunkSave` per modified chunk: cell delta + sidecars (Crops, Trees, Stations, Containers, CraftStations, GroundItems, and UNCOMMITTED: Nests, ForagePools, HostPlants, Broods).

**Triggers:**
1. **Empty-transition (async):** when the last member leaves and `zone.Members==0`, snapshot synchronously then `go writeZoneRecords(...)` (match.go:742-747). The live paused match remains source of truth; this is a restart backup.
2. **10-min autosave (async):** in MatchLoop, past the empty-pause guard — quote (match.go:836-841):
   > `if worldState.TickCount-worldState.LastZoneSaveTick >= zoneAutosaveTicks {` … snapshot sync, `go writeZoneRecords`. `zoneAutosaveTicks = 6000` (~10 min at 10 Hz; only fires while occupied, "exactly when crash-safety matters", zone_persist.go:245-247).
3. **MatchTerminate (SYNCHRONOUS):** the authoritative clean-restart save — `writeZoneRecords(ctx,...)` inline, *not* detached, because a goroutine could be killed during teardown; graceSeconds covers the write (match.go:1592-1597).

All three call the same `snapshotZoneState` (zone_persist.go:404-452), which marshals bytes **synchronously on the match goroutine** (frozen snapshot, immune to later mutation). `ModifiedChunks` **merges** chunks touched this session with prior-modified chunks not revisited (their DB records left untouched) so a farm in an unvisited chunk isn't dropped (zone_persist.go:426-432).

**Versioning:** `zoneStateVersion = 1` (zone_persist.go:27). On mismatch, records are **silently skipped** — `restoreSwarms` bails to fresh spawns (zone_persist.go:144-146), `LoadChunkSaves` drops the record (zone_persist.go:237-239). No migration path; a version bump = "treat as pristine/partial." (Note the CraftStation legacy-shape handling is done at the JSON layer, not via version.)

**Restore ordering (the subtlety):**
1. MatchInit → `prefetchZoneState` loads `:meta` + all `ModifiedChunks` into `state.ZoneChunkCache` (zone_persist.go:253-272). Does **not** apply anything yet.
2. MatchInit → `restoreSwarms` mints **all** clean swarms immediately, before any client joins (match.go:322, zone_persist.go:127-164).
3. Later, per chunk, on first `handleChunkSubscribe`: `LoadChunk` → **`applyChunkSave`** (overlays cells, hydrates sidecars) → **then** the init scans `initFruitTrees/Nests/HostPlants/ForagePools/Stations` (handlers_world.go:36-44). Order is load-critical: restore must precede the init scans because those scans randomize untracked trees/stations and only skip-if-present (zone_persist.go:487-489).

   The **ordering subtlety** you flagged: chunk sidecars (incl. Nests) apply **lazily, AFTER** swarms already exist from step 2. So when a nest's chunk finally applies, its stale `ResidentSwarmID` is cleared and `relinkNestResident` adopts the nearest unlinked same-species swarm *that step 2 already created* (zone_persist.go:535-542 → nests.go:598-637). Swarms-first / nests-lazily-after is exactly what makes the relink find a candidate.

**EphemeralSwarms (test zones):** `restoreSwarms` returns false immediately (always fresh, zone_persist.go:131-135); GroundItems are **neither saved nor restored** (zone_persist.go:378-384 build-side, 560-564 apply-side) — pairs with the fresh-swarm skip so tuning runs don't inherit/accumulate a ground pile (the "immortal-rotten-fruit → 40k items" bug).

**Size constraints:** `local.yml` (`nakama/data/local.yml`) configures only **socket** limits — `max_message_size_bytes: 8388608` (8 MB), `max_request_size_bytes: 8388608`, `outgoing_queue_size: 65536`. Those govern client sockets, **not** server-side `StorageWrite`. There is **no storage-object size limit configured** → Nakama's built-in per-object value cap applies (not overridden here), and there is **no explicit per-record or per-batch guard in the persistence code**. `writeZoneRecords` batches every record (all chunks + meta + swarms) into a **single** `StorageWrite` call (zone_persist.go:456-470). The per-chunk split keeps individual records bounded by a 32×32 chunk; the largest single records are Containers/CraftStations with many `InventorySlot`s.
