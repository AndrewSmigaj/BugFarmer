# Shovel-as-recipe + digging-as-drop: how to hook into the existing systems

## 1. The recipe / crafting system

**Recipe data model** — `nakama/modules/entities/recipe.go:17-26`. Each recipe is:
```go
type RecipeDef struct {
	ID           string     `json:"-"`             // = map key
	Station      string     `json:"station"`       // placeable entity id whose panel offers it
	Inputs       []RecipeIO `json:"inputs"`        // consumed per craft
	Output       RecipeIO   `json:"output"`        // produced per craft
	ProcessTicks int        `json:"process_ticks"` // the ONLY speed knob
	Catalyst     *RecipeIO  `json:"catalyst,omitempty"`
	Unlock       string     `json:"unlock,omitempty"`
	Collection   string     `json:"collection,omitempty"`
}
```
`RecipeIO` (`recipe.go:4-7`) is just `{Item string, Count int}`. Ingredients are a `[]RecipeIO` list → single `Output` RecipeIO. Multi-ingredient is native (e.g. `bed_basic` = 10 plank + 4 cloth, `recipes.json:1715-1734`).

**Data files** — `nakama/data/entities/recipes.json` (a flat JSON object keyed by recipe id; ~230 recipes). Loaded once at `MatchInit` by `LoadRecipes` into `WorldState.Recipes` (map by id) + `RecipesByStation` (per the architecture doc `architecture_crafting.md:13-18`). Client mirror is `BugFarmerClient/Assets/Scripts/Data/RecipeDatabase.cs`.

**Server validate → consume → grant** — the reusable core lives in `nakama/modules/world/craft_stations.go`, and it is **station-agnostic at the item level**:
- `playerHasInputs(player, r)` — `craft_stations.go:192-199`: affordability check over `recipeAllInputs` (inputs + catalyst).
- `consumeInputs(player, r)` — `craft_stations.go:202-206`: removes one batch from the player's bag.
- `recipeAllInputs(r)` — `craft_stations.go:181-189`: flattens inputs + optional catalyst.

These three take **only a `*PlayerState` and a `*RecipeDef`** — no station object, no output grid. That is the key reuse seam for the shovel (see §5).

The full station flow (`craftQueue`, `craft_stations.go:348-394`) validates recipe-belongs-to-station + `recipeKnown`, then loops `playerHasInputs`→`consumeInputs`→`p.Queue++`. Output appears over time via `processCraftStations` (doc `architecture_crafting.md:66-72`); collection uses `addOutput`/`craftCollectOne`/`craftCollectAll` (`craft_stations.go:222-269`).

**Client `CraftingPanel`** — yes: `BugFarmerClient/Assets/Scripts/UI/CraftingPanel.cs` (one singleton panel for both craft stations and chests), reading `RecipeDatabase` + the server echo.

## 2. Could a ground tile be a craftable output / recipe?

**No recipe currently outputs a ground tile.** Every output in `recipes.json` is an inventory item (bars, tools, furniture, walls). Placeable structures (walls/fences/doors) are crafted as *items* (e.g. `wall_stone`, `door_wood`) and then placed by the separate occupant-placement system — they are never a "ground tile."

Two structural facts constrain "place tile X requires [A,B]":
- **The recipe system is bound to a physical station.** `craftQueue` hard-checks `r.Station != s.EntityID` (`craft_stations.go:363`) and `handleCraftStationAction` requires a resolved station in the world (`craft_stations.go:284-288`). A shovel placement has **no station** — the player just clicks a cell.
- **Placement today is not a craft at all** — it is inline in `handleShovel` (§5).

So the cleanest hook is **NOT** to route tile placement through `handleCraftStationAction`. Instead, reuse the *item-level* primitives (`playerHasInputs`/`consumeInputs`) against a **tile-keyed recipe table**. Options:

- **(A) New table keyed by tile/material id** (recommended): e.g. `data/entities/ground_recipes.json` keyed by placed material id (`sand_floor`, `stone_floor`, …) → `[]RecipeIO`. `handleShovel` PLACE looks it up and calls `playerHasInputs`/`consumeInputs` directly. Keeps the "no station" reality honest and doesn't pollute the station recipe graph / integrity gate (`tools/data/recipe_graph.py`, doc `architecture_crafting.md:112-116`).
- **(B) Reuse `RecipeDef` with a sentinel station** (e.g. `station: "shovel"`) so the client `RecipeDatabase`/panel can render have/need. You'd relax the `r.Station != s.EntityID` guard for the shovel path. More reuse of client rendering, but bends the "station = placeable" invariant.

Either way the **consume logic is already written** — you only add data + a lookup + a `consumeInputs` call.

## 4. Drops / ground-item spawning (for digging → drop)

Two identical spawn paths already exist; digging should reuse one.

**Break-with-drops (the model to copy)** — `breakOccupantAt` in `nakama/modules/world/handlers_world.go:504-596`. When breaking a tree/occupant with `withDrops`, it reads `def.GetDrops()` (`[]DropEntry` from `world.breakable.drops`, `entities.go:214-227`) and for each drop:
```go
if state.Rng.Float32() > drop.Chance { continue }
itemID := state.nextItemID(...)
groundItem := &entities.GroundItem{ ID: itemID, ItemType: drop.ItemID, Count: drop.Count, Position: {...}, Lifetime: 60.0 }
state.putGroundItem(groundItem)
m.broadcastToChunk(dispatcher, state, cx, cy, OpCodeGroundItemSpawn, GroundItemSpawnMessage{...})
```
(`handlers_world.go:551-581`). `DropEntry{ItemID, Count, Chance}` (`entities.go:223-227`) is the data shape for a loot table, defaulted in `entities.go:432-437`.

**Simpler single-item spawn** — `spawnHarvestDrops(dispatcher, state, itemType, count, gx, gy, cx, cy)` (`handlers_farming.go:826-866`): one call → one `GroundItem` + `OpCodeGroundItemSpawn` broadcast. This is the easiest primitive for "digging a tile drops N of item X onto the ground."

**Pickup flow** — `handlePickupItem` (`handlers_world.go:721+`): client sends `PickupItemMessage{ID}`; server range-checks (3.0), `player.AddItem`, `state.deleteGroundItem`, sends `SlotUpdateMessage`. (`kill_drops` uses the same spawn path, `handlers_combat.go:207-265`.)

So to make **digging drop items**: instead of the current direct `player.AddItem` (§5), call `spawnHarvestDrops` (or the `breakOccupantAt` loop for a multi-item table) at the dug cell — the pickup/decay/broadcast machinery is already there.

Composites like `grass~dirt~diagNE` are cosmetic; `PrimaryMaterial` governs gameplay, so a recipe keyed by primary material is consistent with everything else.

## Reuse summary (what to build vs. what already exists)

- **Reuse as-is:** `playerHasInputs` / `consumeInputs` / `recipeAllInputs` (`craft_stations.go:181-206`) for the PLACE cost; `spawnHarvestDrops` / `breakOccupantAt` drop loop + `putGroundItem` + `OpCodeGroundItemSpawn` + `handlePickupItem` for the DIG yield; `RecipeDef`/`RecipeIO` shape + `RecipeDatabase.cs`/`CraftingPanel.cs` for client rendering.

- **Replace:** the single-`GroundMaterialItem` cost in `handleShovel` PLACE (`handlers_farming.go:151-160`) and the direct `player.AddItem` in DIG (`handlers_farming.go:127-133`).
