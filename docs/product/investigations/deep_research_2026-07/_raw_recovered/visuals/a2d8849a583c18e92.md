# Round-2 Cold-Critic Verdict — `research_lighting_look.md`

I read the doc in full, re-verified every repo `file:line` it cites, and checked the §6a URP claims against the live Unity 6000.x manuals. Repo claims are **accurate** — I'm not going to relitigate them. The problems that remain are two framing errors the revision introduced or left standing, plus one genuinely-missing Apico technique.

## Round-1 fixes — did they land?

**Fix #1 — recipe now leads with dark ambient (§3). VERDICT: FIXED (as a reordering) — but the underlying thesis over-rotates.**
- Reorder is coherent: §3 Tier 1 leads with dark-colored-ambient, bloom demoted to Tier 2 #4, §7 mirrors it. Internally consistent with the §2 rubric ("#1 lever").
- The claim "ambient tuning is cheaper because the Global Light already exists" is **correct**: `DayNightController.cs:66-89` creates/adopts exactly one Global Light2D and drives its intensity/color every frame (`:132-152`). Tuning it is pure value changes — no new assets. Verified.
- **But** — see NEW #1 below. The "darkness is #1" thesis is imported wholesale from the night/underground research and is now the anchor for the *entire* look, including daytime. That's a real prioritization problem for a mostly-daytime outdoor farm benchmarked on Apico.

**Fix #2 — emission re-costed "needs tooling", contact shadows "runtime decal only" (§4). VERDICT: FIXED CORRECTLY.**
- Pipeline verified: `tools/sprites/pixelclean.py` is RGBA-only, k-means quantize (`kmeans2`, line 91), no emission/normal channel authored anywhere. §4's "new tooling required" is accurate.
- Baked-shadow ban verified: `tools/art/style.json` repeatedly forbids it — `:24` "no cast shadow", `:34` "no ground patch… no cast shadow", `:88`, `:102`. §4's "runtime decal only" is the only compliant path. Correct.
- No residual place assumes emission/normal channels exist: §2 table Glow row states emission as a *technique*, and the Form row explicitly flags normals "unsupported by our pipeline; defer"; source table (`:140`) says "no pipeline support here." Consistent.

**Fix #3 — §3a pixel-art/bloom failure-mode + PPC decision. VERDICT: MOSTLY FIXED, but §3a introduces a NEWLY-MISLEADING line.**
- §3a now exists and is adequate as a research flag: bloom-softens-crisp-edges, top-down readability risk, explicit PPC decision, "readability at game zoom" added to rubric. Good. (There's a real PPC+post gotcha it doesn't mention — post-processing breaks under PPC "Stretch Fill" crop — but PPC isn't even in the project, so flagging it as an open decision is fine.)
- **The "scoped to an emissive layer" recommendation is not achievable natively in URP 2D and misleads.** URP Bloom is a whole-camera Volume post effect; there is no sorting-layer/render-layer scope toggle. Layer-scoped bloom requires a **custom ScriptableRendererFeature / render pass or a second-camera composite** (Unity's own docs: layer-restricted rendering is a *custom render pass* feature — [custom-rendering-pass-workflow](https://docs.unity3d.com/Packages/com.unity.render-pipelines.universal@14.0/manual/renderer-features/custom-rendering-pass-workflow-in-urp.html)). This is *more* engineering than the emission-mask tooling the doc is careful to cost in §4 — yet §3a presents it as the "ideal" easy path. The native mechanism the doc already knows (§2: "Bloom threshold ~1") is threshold + HDR emission, so only intended-bright pixels bloom. §3a should say that, not "emissive layer."

**Fix #4 — flicker (T1), dappled/cloud shadows, in-beam particles, weather grading. VERDICT: FIXED CORRECTLY (one still-missing technique).**
- All four present: flicker §3 T1 #3 + §2 + §5 + §7; dappled/cloud shadow §3 T3 #8 + Stardew row; in-beam particles §3 T3 #8; per-weather grade §3 T3 #7 (with an honest "couldn't source Apico grades on rain" caveat in §5 — good discipline).
- **Flicker-in-Tier-1 is justified**: near-zero cost (a few lines in `LampLight.cs` `Update()`), provably absent (`LampLight.cs:43` is `intensity = _baseIntensity * (1f - Daylight)`, no noise term), high cozy payoff, and it's "tuning existing code" which is what Tier 1 *is*. Minor caveat: lamps fade to 0 in daytime (`:43`), so flicker only pays off at night/underground — calling it a top-3 *look-dominating* lever slightly overstates for a daytime-dominant game, but including it in T1 is correct.

**Fix #5 — §6a URP prerequisites. VERDICT: TECHNICALLY CORRECT.**
- (1) HDR already on — verified `UniversalRP.asset:26 m_SupportsHDR:1`.
- (2) Raise HDR Emulation Scale so lamps (not just sprites) bloom — **correct.** At scale 1, 2D lights are clamped to a max contribution of 1; the emulation scale is the extra intensity range that lets them exceed 1 ([HDR emulation scale docs](https://docs.unity3d.com/6000.4/Documentation/Manual/urp/2DRendererData-overview.html); banding at high values confirmed). Verified `Renderer2D.asset:31 m_HDREmulationScale:1`.
- (3) Switch Color Grading Mode to HDR when tonemapping — **correct.** Unity: "Tonemapping should always be applied when using an HDR camera; otherwise any color intensity above 1 will be clamped at 1" and grading mode falls back appropriately ([HDR Output / grading docs](https://docs.unity3d.com/6000.0/Documentation/Manual/urp/post-processing/hdr-output.html)). Verified `UniversalRP.asset:80 m_ColorGradingMode:0` (LDR).
- (4) LUT import Read/Write on, compression off, non-sRGB — standard-correct; and the 1024×32 size matches `UniversalRP.asset:81 m_ColorGradingLutSize:32`. Verified.
- (5) camera post flag + real-valued scene Volume — verified `SampleScene.unity:898 m_RenderPostProcessing:0`, `m_VolumeProfile:{fileID:0}`, and the `DefaultVolumeProfile.asset` overrides are all `active:1` at no-op values (Bloom intensity 0 / threshold 0.9, Tonemapping mode 0, ColorLookup contribution 0, Vignette intensity 0, ColorAdjustments neutral). Verified.
- The one HDR-Output source-table line (`:136`) is also correct: the real limitation is "SDR rendering **+ HDR Output** on 2D Renderer requires post OFF" — which does not bite an SDR-display target, so "not a blocker for SDR" is the right conclusion (terse, but not wrong).
- Missing from §6a: no mention that too-high HDR Emulation Scale causes **banding** (the doc never says this anywhere). Minor.

## NEW material findings (ranked)

**1. (Material) The doc over-corrected: "dark colored ambient is the #1 anchor" is a night/underground truth mis-applied as the universal daytime anchor — and it mismatches Apico.** Apico's actual look: "During day time there's no special effects to the overworld"; dawn/dusk add a warm glow + god rays; the world is "bright… colorful biomes" ([APICO Time wiki](https://wiki.apico.buzz/wiki/Time), [APICO biomes/review](https://switchplayer.net/2022/08/12/apico-review/)). During the dominant gameplay state (day), Apico is bright and flat-lit — the cozy read comes from **palette grade + warm/cool + soft glow + light shafts**, not from darkening. Round 1 the doc led with bloom (wrong); round 2 it swung to "make it dark first" (also wrong for daytime). The honest answer is context-split: darkness-first is right for **night/interiors/underground** (the sibling doc's domain), but the **daytime Apico-matching look leans on grade + glow + beams**, which the reorder pushes to Tier 2/3. Anchoring the whole implementation priority on a lever that does nothing at noon is a real misdirection.

**2. (Material) "Scope bloom to an emissive layer" (§3a) misleads about engineering cost.** Not a native URP 2D toggle — needs a custom render pass or second-camera composite. Replace with the native path the doc already knows: high Bloom **threshold + HDR emission** so only intended emitters bloom; note true layer-scoping as a custom-pass cost if ever wanted. As written it could send an engineer down a custom-render-feature rabbit hole, or let a designer assume it's free. (Detail under Fix #3.)

**3. (Moderate) Missing Apico technique: god-ray / light-shaft overlays.** Apico's signature dawn/dusk tell is literally "god rays falling from the left/right" ([APICO Time wiki](https://wiki.apico.buzz/wiki/Time)). The doc has "in-beam particles" (dust motes) but never lists the **volumetric light shaft / god-ray overlay** itself — a cheap additive-sprite/soft-beam technique that is arguably the most recognizably-Apico outdoor cozy element. Add it to Tier 3 atmosphere alongside dappled shadows.

**4. (Minor) Internal tension in §1's HDR-emulation parenthetical.** §1 says at scale 1 "bloom otherwise catches only emissive *sprites*, not the Light2Ds" — but §4 correctly establishes the pipeline authors **no emissive sprites either**. So at the current config, bloom catches essentially *nothing* (except the additive lightning flash). This actually strengthens the doc's own conclusion (raising HDR Emulation Scale is required for *any* lamp bloom), but the parenthetical implies emissive sprites already glow, which they don't. One-line tightening.

## Ship-ready for design?

**Yes as a research/working doc — with two edits required before its conclusions graduate into `architecture_lighting.md`.** Every verified claim (repo config, scripts, pipeline, §6a URP prerequisites) is accurate, and four of five round-1 fixes landed correctly. But two framing issues are material enough to distort implementation if they graduate unchanged:

1. **Split the "darkness-first" anchor by context** — darkness-first for night/underground; **grade + soft glow + light shafts** for the daytime outdoor look that actually matches the Apico benchmark. Don't present dark-ambient as the single universal anchor.
2. **Fix the §3a bloom line** — "high Bloom threshold + HDR emission (native)"; flag "scope to a layer" as a *custom render pass* cost, not the easy/ideal path.

Both are edits, not re-research. Add god-rays (NEW #3) while you're in there. With those, it's a defensible spine for the design doc. Without #1 especially, the team could correctly execute a look that's optimized for a cave and wrong for a sunny farm.
