## 1. The plan spine is ordered wrong, and the doc contradicts itself on it — MOST MATERIAL

**What's wrong:** §3/§7 make "turn the pipeline on (Bloom) first" the anchor win. But the doc's OWN acceptance rubric (§2, row 1) says the #1 tell is *"Dark, colored ambient multiplier… Darkness is what makes light read as light."* Those two can't both be the lead. The darkness/ambient change is the one that dominates the look, and it's the cheaper of the two here — it's pure tuning of the **Global Light that already exists** (no new assets, no profile authoring). Bloom's headline payoff ("glowing things glow") is gated behind emission maps, which the doc itself defers to Tier 2 and which don't have tooling yet (see finding 2). So "bloom first" front-loads the effect whose value is *most* blocked.

**Evidence:** The doc's §2 table literally states darkness is the mechanism; §3 Tier 1 step 2 is the ambient change and step 1 is post-processing — the ranking inverts the doc's own thesis. Project-side, the Global Light + `DayNightController.Daylight` ramp already exist (`LampLight.cs:43` reads `DayNightController.Daylight`), so the ambient pass is a tuning change on live code, whereas bloom needs a Volume + authored profile that don't exist (`UniversalRP.asset:95` → `m_VolumeProfile: {fileID: 0}`, camera `m_RenderPostProcessing:0`).

**Fix:** Lead with the dark-colored-ambient pass (or make it co-equal step 0). Reframe bloom as "reveals the light you've already created once ambient is dark," not the standalone anchor. State explicitly that bloom-before-dark-ambient will underwhelm because there's nothing dark for glow to pop against.

## 2. Tier 2 "emission maps (Low cost)" assumes a workflow that does not exist in this project — MATERIAL

**Evidence:** `docs/guides/art/object_pipeline.md` — Pipeline A is `gen_sprites.py → pixelclean.py → make_scene.py`; `pixelclean.py` "palette-quantize (k-means) per asset" to as few as 8 colors; the "Future direction (not built yet)" section lists only animation, not multi-channel authoring. ## 3. Missing failure mode: bloom on crisp pixel art, with NO Pixel Perfect Camera — MATERIAL

**What's wrong:** This is a pixel-art game (Point filter, palette-quantized, integer NEAREST upscale) and the owner benchmarks a pixel-art game. Full-screen bloom haloes and softens exactly the crisp edges that pixel art depends on, and in a **top-down** game that also risks washing out gameplay readability (crops/bugs/UI-relevant glows). The doc treats "turn on Bloom" as pure upside and never raises this tension. Worse, there is **no Pixel Perfect Camera in the project at all** — so upscaled pixels aren't grid-snapped, and running post over a non-pixel-perfect upscaled buffer can amplify shimmer.

**Evidence:** `object_pipeline.md` sets `filterMode:0` (Point) and NEAREST upscale at PPU 16; `pixelclean.py` quantizes to ~8 colors — this is hard pixel art. Grep for `PixelPerfectCamera` / `com.unity.2d.pixel-perfect` across `Assets/` and `Packages/manifest.json` returns **nothing**. External confirmation that bloom fights pixel art: [Unity 2D Pixel Perfect manual](https://docs.unity3d.com/Packages/com.unity.2d.pixel-perfect@1.0/manual/index.html) exists precisely to keep pixels "crisp and stable in motion," and pixel-art guidance is that bloom "adds a glowing halo around bright pixels… making it appear washed out rather than crisp."

**Fix:** Add a "pixel-art integration" subsection: keep bloom **low-threshold/subtle**, ideally scope it to an emissive layer rather than the whole frame; decide the Pixel-Perfect-Camera question explicitly (add the component or accept the shimmer trade-off) *before* enabling full-screen post; add "readability at game zoom" to the acceptance rubric.

This belongs in Tier 1 — it's a few lines on the existing component.

Reference appetite: Stardew's [Dynamic Shader mod](https://www.nexusmods.com/stardewvalley/mods/40775) ("dynamic shadows that evolve with time and weather").

## 5. URP claims that are correct-but-incomplete, plus two config knobs the doc never mentions

The doc's URP assertions mostly survive verification (credit below), but it omits the project-specific settings that actually gate the bloom story:

- **2D-renderer HDR Emulation Scale.** The doc says "HDR emission color >1 needed for Bloom" but never mentions the 2D Renderer's own `m_HDREmulationScale` (currently **1** in `Renderer2D.asset:31`). In the 2D renderer this scale governs the HDR range for 2D lights/emission — it's the knob that decides whether values can actually exceed 1 to trip the bloom threshold. Not mentioning it means "set emission >1" can silently do nothing.
- **Color grading mode is LDR.** `UniversalRP.asset:80` `m_ColorGradingMode: 0` (Low Dynamic Range). The doc recommends Tonemapping + Color Adjustments, but LDR grading clamps HDR before grading, blunting tonemapping/bloom interaction. HDR grading mode is the usual recommendation once you're doing HDR bloom. Unmentioned.
- **LUT import gotchas.** The doc's "1024×32 neutral LUT" is right (and matches this project's `m_ColorGradingLutSize: 32`), but external Color Lookup textures need Read/Write on, compression off, and non-sRGB/bilinear or you get artifacts ([Unity discussions on LUT import](https://discussions.unity.com/t/where-to-download-a-urp-postprocessing-neutral-color-lut-16-and-32/767520)). Unmentioned.
- **Niche caveat worth one line:** the 2D Renderer + HDR *display* Output path requires post-processing OFF ([Unity 6 HDR Output manual](https://docs.unity3d.com/6000.4/Documentation/Manual/urp/post-processing/hdr-output.html): *"To use SDR Rendering with HDR Output on the 2D Renderer, you must ensure post-processing is turned off."*). Not a blocker for SDR displays, but the doc's "just turn everything on" framing should acknowledge it.

**Fix:** Add a short "URP config prerequisites" checklist: verify URP-asset HDR (already on — `m_SupportsHDR:1`), set/raise 2D HDR Emulation Scale, switch grading mode to HDR if tonemapping, and the LUT import settings.
