6. **Write ground:** `chunk.Ground[ly][lx] = newTile` (`:292`).
7. **Broadcast:** `m.broadcastWorldUpdate(dispatcher, state, cx, cy, gx, gy, newTile, nil, false)` (`:295`).

## 4. Persistence

Ground edits persist as a **semantic diff** vs the authored zone, and the ground id is stored as an **opaque string** — a composite id round-trips unchanged.

**Type** — `/mnt/c/Users/emily/BugFarmer/nakama/modules/world/world_save.go:37-43`:
```go
type GlobalCellEdit struct {
    GX     int             `json:"gx"`
    GY     int             `json:"gy"`
    Ground *string         `json:"ground,omitempty"`
    Occ    json.RawMessage `json:"occ,omitempty"`
    OccSet bool            `json:"occ_set,omitempty"`
}
```

**Save** (`world_save.go:124-142`) — diffs live ground against the authored base; any string difference is captured verbatim:
```go
if liveG, baseG := groundAt(live, lx, ly), groundAt(base, lx, ly); liveG != baseG {
    g := liveG
    edit.Ground = &g
    changed = true
}
...
ws.CellEdits = append(ws.CellEdits, edit)
```

**Load** (`world_save.go:365-372`) — writes the stored string straight back into the chunk:
```go
for _, e := range ws.CellEdits {
    ...
    lx, ly := e.GX%ChunkSize, e.GY%ChunkSize
    if e.Ground != nil {
        chunk.Ground[ly][lx] = *e.Ground
    }
    ...
}
```
No parsing, canonicalization, hashing, or validation of the ground string on either side — `grass~dirt~diagNE` is stored and restored byte-faithfully. **Persistence is fully composite-safe.** (One consequence to be aware of: because save is a *diff vs authored base*, any composite id you set will always differ from the authored tile and thus always be persisted — expected and fine.)

## Where an arbitrary/composite ground id would break (flags)

1. **CLIENT RENDERING — the real blocker.** The client resolves a ground id to a sprite by filename: `TilemapManager.SetGroundTile` (`TilemapManager.cs:951-986`) calls `TileDatabase.Instance.GetGroundTile(tileId)`, which does `Resources.Load<Texture2D>($"Tiles/{tileId}")` (`/mnt/c/Users/emily/BugFarmer/BugFarmerClient/Assets/Scripts/World/TileDatabase.cs:45-73`). There is **no `~` parsing, no blending, no composite handling** — a composite id `grass~dirt~diagNE` looks for `Resources/Tiles/grass~dirt~diagNE.png`; if absent it logs a warning and returns a **magenta fallback tile** (`GetFallbackTile`, `:75-90`, `color = magenta`). So unless you either (a) add a PNG per composite permutation, or (b) add composite-parsing/blending logic in `TileDatabase`/`SetGroundTile`, every shovel-placed composite renders as magenta. This is new work the shovel feature must add.

2. **SERVER tile semantics — silent degradation, not a crash.** Ground ids are looked up in `state.TileDefs` for gameplay properties. A composite id absent from `tiles.json` returns `nil`:
   - Bug collision `IsBlocked`: `tileDef := w.TileDefs[tileID]; if tileDef != nil && tileDef.BlocksBugs` (`state.go:615-616`) → unknown = treated as non-blocking.
   - Player movement uses the same TileDefs path (`IsBlockedForPlayers`, `handlers_world.go:626+`) and `MovementMult` — unknown = walkable, speed multiplier defaults.
   - Planting: `handleSeedPlanting` (`handlers_world.go:313-317`) requires `tileDef != nil && tileDef.AcceptsPlant` → you cannot plant on an unknown composite tile.
   - Re-hoeing: `handleHoe` (`handlers_farming.go:271-275`) errors "Unknown tile" if `state.TileDefs[tile] == nil`.
   None of these crash, but a composite id not registered in `tiles.json`/`TileDefs` loses movement/collision/plantability semantics. If the composite is meant to behave like `dirt`, you either need each composite id registered in `TileDefs`, or a server-side "strip the composite decoration to a base id" resolver for property lookups.

3. **No server validation of the chosen id.** If you send a player-chosen `ground_id`, nothing today rejects a garbage/oversized/malicious string — it will be written to `chunk.Ground`, broadcast, and persisted. You will need to **add validation yourself** (e.g. parse the composite into `base~overlay~shape`, verify each part against a known set, cap length) — there is no existing gate to lean on.

**Summary:** persistence (§4) and server broadcast (§5) are already fully opaque-string-safe and need no changes. The composite id will round-trip and replicate untouched. The work the shovel needs that the hoe flow does NOT already provide: (a) a `"shovel"` case in both the client `PlayerInputRouter` switch and the server `handleToolUse` switch; (b) a **new field/message** to carry the player-chosen id (no precedent exists — all current ground messages are coordinates-only and server-computed); (c) **server validation** of that arbitrary id; (d) **client composite-tile rendering** in `TileDatabase`/`SetGroundTile` (today → magenta fallback); and (e) registering composite ids (or a base-id resolver) in `TileDefs` so movement/collision/planting keep working.
