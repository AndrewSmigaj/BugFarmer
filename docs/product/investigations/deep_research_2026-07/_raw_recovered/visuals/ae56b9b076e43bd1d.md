## 1. The `Light2D` types — what each is and when to use it

The `Light2D.LightType` enum (URP 17): `Parametric = 0`, `Freeform = 1`, `Sprite = 2`, `Point = 3`, `Global = 4`. (In code our Global light is `m_LightType: 4`, lamps are `LightType.Point`.)

- **Global** — "Lights all 2D GameObjects equally with no attenuation." Ambient/base fill. **Only one Global per Blend Style per sorting layer.** No shadows, no volumetrics, no normal-map interaction. This is our day/night light.
- **Spot** (labeled "Spot" in the inspector; the enum value is `Point`) — "Emits light from a point… with a cone-shaped area of effect." A radial point light when Inner/Outer angle = 360, or a cone when the angle is narrowed. This is our `LampLight` (angles 360 = round glow) **and** our flashlight (Inner 30 / Outer 70 = cone). This is the workhorse for lamps/torches.
- **Freeform** — "Emits light as a custom polygon shape you can edit" with a spline + Falloff handle. Use for shaped area glows (a window rectangle, a lava pool). More expensive to author; we don't use it.
- **Sprite** — "Emits light in the shape of a sprite." Assign any sprite to the **Sprite** field; the light takes that sprite's silhouette/gradient. This is the "soft cookie" trick (section 4).
- **Parametric** — deprecated since URP 11; a converter upgrades it to Freeform. Don't create new ones.

### Key inspector fields (exact names)
- **Color** — light tint; can go over 1 when combined with HDR Emulation Scale.
- **Intensity** — brightness, default 1; values >1 push into HDR (our Global lerps night-floor→1; our lamps scale by `1 − Daylight`).
- **Radius → Inner** — "radius inside which the light has maximum intensity." **Radius → Outer** — "radius where the light stops." (Our `LampLight` sets Outer = radius, Inner = radius × 0.25 → a soft-ish core; the flashlight is Outer 8 / Inner 0.5.)
- **Inner / Outer Spot Angle** — cone angles (360/360 = full circle; 30/70 = flashlight cone). Light fades between inner and outer angle.
- **Falloff / Falloff Strength** — how fast intensity decays between the inner and outer radius (and between the angles). Serialized as `m_FalloffIntensity` (our Global = **0.5**). Higher = softer, more gradual edge; 0 = hard cutoff. **This is your main "soft look" dial** and it's the one our lamps leave at default → the "hard falloff" you flagged.
- **Blend Style** — which of the Renderer's blend-style slots this light writes into (`m_BlendStyleIndex`; ours = 0 = Multiply).
- **Light Order** — render order among lights sharing a blend style (matters with Alpha-Blend overlap).
- **Overlap Operation** — Additive (default; overlapping lights add) vs Alpha Blend (one overrides, ordered by Light Order).
- **Shadow Strength** (a.k.a. Shadow Intensity, `m_ShadowIntensity`) — 0 = blocks nothing, 1 = blocks all; needs Shadow Caster 2D to do anything (ours is 0.75 but nothing casts yet).
- **Volumetric Intensity** — 0 = invisible in empty space, 1 = fully visible fog-like beam (not on Global).
- **Normal Map Quality** (Disabled / Accurate / Fast) + **Normal Map Distance** — see section 3 (not on Global).
- **Target Sorting Layers** — which layers this light affects (`m_ApplyToSortingLayers`).

## 2. Light Blend Styles (Multiply vs Additive, mask variants) + the perf rule

Blend styles are defined in the **Renderer 2D asset**, not per-light; each light just picks a slot. Our `Renderer2D.asset` has the four defaults:

| Slot | Name | maskTextureChannel | blendMode |
|---|---|---|---|
| 0 | Multiply | 0 | 1 (Multiply) |
| 1 | Additive | 0 | 0 (Additive) |
| 2 | Multiply with Mask | 1 | 1 |
| 3 | Additive with Mask | 1 | 0 |

- **Multiply** darkens toward the light color where unlit — this is the correct choice for a **global day/night ambient** and general scene lighting (a Multiply global at low intensity = darkness; at 1 = full day). It's why our Global uses slot 0.
- **Additive** adds light on top — right for glowing accents (a torch bloom, magic) layered over a Multiply base.
- **…with Mask** variants read a sprite's `MaskTex` secondary texture channel so a light only affects masked regions.
- Each slot's **Blend Mode** can be Additive / Multiply / Subtractive / Custom (custom weights); **Mask Texture Channel** selects R/G/B/A.

**The performance rule (verbatim):** "each different blend style you use creates a new light **render texture**… use only **one or two** different blend styles in a scene." Each blend style is a full Render Texture that must be rendered and uploaded every frame. **Our project already uses exactly one (Multiply)** — optimal. If you add torch glows, prefer keeping them on Multiply, or accept at most one extra Additive slot.

**Overlap Operation** (per light): Additive is the default (overlapping red+blue → magenta); Alpha Blend makes the higher-**Light Order** light win instead of summing.

## 3. Normal maps via Secondary Textures (`_NormalMap`) — relief + the depth-prepass cost

**Setup (exact):** select the sprite's source texture → **Open Sprite Editor** → top-left dropdown → **Secondary Textures** → **+** → set **Name = `NormalMap`** (or `MaskTex`), drag the normal texture into **Texture** → **Apply**. The names must be exactly `NormalMap` / `MaskTex` — "Naming these Textures correctly allows them to interact with the 2D Lights Shaders." Secondary textures are "sampled with the same UV coordinates as the Texture of the selected Sprite," so they must align pixel-for-pixel. The sprite must use a **Lit** material (`Sprite-Lit-Default`) for the shader to sample it — an unlit sprite ignores the normal map.

**Effect:** a normal map gives each pixel a surface normal, so a flat sprite reacts to a light's direction — highlights on the lit side, shadow on the far side — creating fake 3D relief that shifts as lights move. Global lights **cannot** use normal maps (no direction); only Spot/Freeform/Sprite lights do, gated by the light's **Normal Map Quality**:
- **Disabled** — ignore normals (cheapest).
- **Accurate** — best quality.
- **Fast** — cheaper approximation; "artifacts may occur." Doc guidance: "**smaller lights and larger [Normal Map] distance values reduce the difference between fast and accurate**," so for small lamp lights you can safely use Fast.
- **Normal Map Distance** — the perceived Z distance between light and sprite (our scene's Global carries `m_NormalMapDistance: 3`, `m_NormalMapQuality: 2` in serialized form, though Global ignores them).

**The performance cost (quantified as the docs allow):** "Adding a normal map means Unity adds a **depth pre-pass for each layer batch that renders a full-size render texture**." So enabling normals is not per-sprite-cheap — it adds a full-screen pass **per layer batch**, on top of the normal-map sampling. **For our case** (pixel art at PPU 16, many pooled SpriteRenderers) this is the expensive lever: turning normal maps on introduces that full-size prepass and, if lights target multiple sorting layers/batches, one prepass each. Recommendation: if you want relief, apply normal maps to a **few** hero elements on **one** sorting layer, keep light **Normal Map Quality = Fast** for the small lamp lights, and measure — don't blanket-enable on every pooled sprite.

## 4. Sprite `Light2D` as a soft "cookie" (radial-gradient sprite instead of hard falloff)

Instead of a Point light with a hard/procedural falloff, use a **Sprite**-type `Light2D`:
1. Create a texture that is a **soft radial gradient** (bright white center → transparent edge; a feathered blob). Import as a Sprite.
2. Add a `Light2D`, set **Light Type = Sprite**, and assign that texture to the **Sprite** field.
3. The light now takes the sprite's exact shape *and its alpha gradient as the falloff* — the softness is baked into the texture, giving a much softer, art-directable edge than the Point light's Falloff Strength can. Scale/rotate the transform to size it; tint with **Color**, drive brightness with **Intensity**.

This is the standard fix for "point lights look like hard discs": a soft cookie sprite reads as a gentle pool of light. For our lamps you could swap the Point `LampLight` for a Sprite light using a shared soft-gradient sprite — but note a Point light with a raised **Falloff Strength** (section 6) gets you 80% of the way with zero extra texture. Sprite lights are the move when you want a *specific shape* (a lantern's teardrop, a window's rectangle) or extra-soft edges.

## 5. Global Light for ambient/darkness; layering warm+cool; soft falloff tuning

- **Global for ambient/darkness:** exactly what our `DayNightController` does — one Global (Multiply, blend index 0). Its **Intensity** is the master brightness: our code lerps a **night floor (0.20)** up to **1.0** across the day curve, so at deep night the whole world sits at 0.20 and you only see inside lamp radii. **Only one enabled Global per blend style** — our controller explicitly adopts the first Global and disables extras, because two Globals at intensity 1 both accumulate into the Multiply texture and pin the world bright (the "night isn't dark" bug, called out in the code comment).
- **Layering warm + cool:** tint the Global by time — our code lerps a **moonlit-blue night** (`0.35, 0.42, 0.75`) → a **warm amber dawn/dusk** (`1.0, 0.80, 0.58`) → white day. Then the **warm lamp Point lights** (`1.0, 0.97, 0.85`) read strongly against the cool night ambient. This warm-key/cool-ambient contrast is the single biggest "looks good" trick, and it works because Multiply-global + Additive-feeling point lights combine.
- **Falloff tuning for softness:** raise the light's **Falloff Strength** (`m_FalloffIntensity`) toward ~0.6–0.9 for lamps so the edge feathers instead of ending in a hard ring. Our lamps currently inherit the default (the "hard falloff" you flagged) even though `Inner = 0.25 × Outer` already gives a soft core; the missing dial is Falloff Strength. Pair a slightly larger **Outer Radius** with a small **Inner Radius** and a high Falloff Strength for the softest pool. For pixel art specifically, some devs also lower the Renderer's **Light Render Texture Scale** to intentionally chunk/soften light edges to match the pixel grid.

## 6. Bloom via a URP Volume on emissive/lights — and how "emissive" works for a 2D lit sprite

**Requirements (all three):** (1) **HDR on** — our `UniversalRP.asset` already has `m_SupportsHDR: 1`, so bright pixels aren't clamped to 1 before post; (2) **post-processing ON on the camera** — ours is currently **`m_RenderPostProcessing: 0`, i.e. OFF**, so bloom cannot run today even though HDR is on; (3) a **Volume** (Global or box) in the scene with a **Bloom** override.

**Bloom Volume Override fields:** **Threshold** (gamma brightness where bloom starts, default 0.9 — set it *below* your emissive brightness or nothing glows), **Intensity** (0 = off; raise it), **Scatter** (radius 0–1, default 0.7 — higher = wider glow), **Tint**, **Clamp** (max input intensity, default 65472), **High Quality Filtering** (bilinear, smoother but costlier), **Downscale** (Quarter = cheaper) and **Max Iterations** (default 6) for perf, plus **Lens Dirt** Texture/Intensity.

**How "emissive" is expressed for a 2D lit sprite** — two ways, and this is the crux of your question:
- **HDR light intensity:** because bloom keys off pixels brighter than 1, a `Light2D` with **Intensity > 1** (multiplied by the Renderer's **HDR Emulation Scale**, ours = 1) pushes lit pixels into HDR, and bloom then blooms the lit region. So a bright lamp naturally glows once post is on — no special material needed.
- **Additive overlay / emission sprite:** `Sprite-Lit-Default` has **no emission channel**, so a lit sprite can't "self-glow" from its own texture. To make a *specific part* of a sprite glow (a torch flame, glowing eyes) regardless of scene light, overlay an **additive** sprite (an Unlit sprite with an HDR/over-1 color, or an additive-blend material) on top — that pixel exceeds 1 and blooms. For full control, a **Shader Graph Sprite Lit** sub-target with an explicit HDR **Emission** output is the clean route.

**Bottom line for us:** to get glow you'd (a) enable `m_RenderPostProcessing` on the camera, (b) add a Global Volume with a Bloom override (Threshold ~0.8–1.0, Intensity ~0.3–1, Scatter ~0.7), and (c) either bump key lights above Intensity 1 or add additive HDR overlay sprites for point-emissive art. HDR is already on, so only the camera flag + Volume are missing.
