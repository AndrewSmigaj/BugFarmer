## Distilled IMPACT-FEEDBACK SPEC

**When to fire — the contact frame.** Compute it as a fraction of the swing coroutine's duration, not a network event. Contact = **~65% through the swing** (the fastest point of the arc per SLYNYRD/GDKeys). Fire an internal `OnToolContact()` callback there. **Everything below fires on that one frame, in the same call.** Today's bug is that this stack is triggered by the server break-progress tick; move it to this animation-driven callback.

**The stack (all client-local, all cosmetic):**

1. **Hitstop / hitlag — ~40–90ms**, scaled by hit weight:
   - Light tap (grass, small object): **2–3 frames ≈ 33–50ms**.
   - Normal tool strike (tree/ore chip): **4–5 frames ≈ 66–83ms**.
   - Heavy / final breaking blow: **6–8 frames ≈ 100–130ms** (cap ~130ms; don't approach Mordhau's 350ms for a farm tool — too sluggish).
   - **Implementation:** do NOT touch global `Time.timeScale`. In multiplayer that pauses every local object's `deltaTime`-scaled logic and every coroutine using `WaitForSeconds`, and it stutters other players' interpolated movement on this client. Instead **pause only the swing animation + the struck target's wobble** (freeze their local anim playhead), or better, **ramp the swing coroutine's playback speed down→up across contact** (Ahmad's curve approach). The server tick is on its own clock and is untouched either way — but per-object pause is the clean, side-effect-free choice.

2. **Screenshake — trauma model (adopt roystan/Eiserloh numbers):**
   - Add trauma on contact: **light +0.2, normal +0.35–0.4, break +0.5–0.6** (clamp to 1).
   - `shake = trauma²`; decay `trauma -= dt * 1.5`; Perlin `frequency ≈ 25`.
   - 2D magnitudes: **max translation ≈ 0.15–0.3 world units** (roystan's `(1,1,1)` is tuned to its scene scale — start smaller for a cozy farming cam and tune up), **max angular ≈ 1–2°** (keep rotation subtle for top-down; 15° is too much for farming — that range suits an action shooter).
   - **Directional kick (Vlambeer camera-kick):** add a one-shot camera offset of a few px **in the swing direction** (away from player toward the struck cell) that springs back, layered on top of the noise shake. This directionality reads as "the tool drove into it."

3. **White flash on the struck object — 1 frame on, ~2–3 frames fade (≈50–80ms):** swap the target sprite to a white-tinted material/`_Color` then lerp back. Cheapest, highest-impact "confirmation" effect.

4. **Squash / wobble on the target — ~80–120ms:** brief scale punch (e.g. 1.0 → 1.12/0.9 → 1.0) on the struck object, decaying. Pairs with the flash.

5. **Particle burst at the contact point — one-shot, cheap, layered:**
   - **6–12 chips/sparks** (material-appropriate: wood chips, stone chips, dirt/dust puff), emitted in a cone opposite the swing, gravity-affected, ~0.3–0.5s lifetime.
   - Optionally a single **dust/impact "poof"** sprite that scales up and fades (~120ms). Layering 2–3 cheap effects (chips + dust + flash) reads richer than one expensive one — the Vlambeer/GMTK lesson.

6. **SFX on the same frame** — impact sound (randomized pitch ±, and optionally rising pitch on a combo/streak per GMTK). Firing SFX on contact rather than the tick is a big part of the "connected" feel.

## The decoupling pattern (network-tick → contact frame)

**Core principle from the domain:** in a client-authoritative-*feel* game, **cosmetic feedback is predicted locally on input and reconciled by the server.** The player swings → the client immediately plays the full swing + fires the entire juice stack at its own contact frame. The server's authoritative break/damage arrives whenever it arrives (later, over the network) and only reconciles **state** (did the object actually break, drops, HP). The two are decoupled:

- **Swing animation + juice stack** = driven by the local swing coroutine's timeline. `OnToolContact()` at ~65% → fire hitstop/shake/flash/particles/SFX. This is what the player feels.
- **Authoritative result** = server break-progress tick. It updates the world model (object destroyed, item spawned) but should **no longer be the trigger for the juice** — at most it triggers a *terminal* effect (the object's death/shatter burst) when the break actually completes.

**Risk flags for a networked/deterministic sim:**
- **Never use global `Time.timeScale` for hitstop.** It is client-local (won't desync the server, which runs its own tick), but it stutters *other players'* interpolated movement/anim on this client and pauses unrelated `WaitForSeconds` coroutines. Use per-object animation pause / play-rate ramp instead.
- **Keep all of this out of the deterministic sim entirely.** Per your `frontier-sync` model, cosmetic feedback needs **no ledger event** — it must not read or write anything the bug-sim hashes. Contact-frame timing, trauma value, particle RNG, flash state = pure client presentation. Seed particle/shake RNG from a local (non-sim) source so it can't perturb determinism.
- **Prediction mismatch:** if the client predicts a strike but the server says the object was already gone (someone else broke it, or a click-steal), suppress or gracefully cancel the terminal break burst — but the *impact* juice (flash/spark/shake) having already fired is fine and even desirable (it still felt responsive). Only the authoritative *outcome* reconciles.

---

**Bottom line:** move the existing feedback trigger from the server break tick to an animation-driven `OnToolContact()` at ~65% of the swing; fire a stacked hitstop (per-object, 40–130ms by weight) + trauma shake (`trauma²`, +0.2–0.6, decay 1.5/s, freq 25, small 2D translation + tiny rotation + directional kick) + 1-frame white flash + scale-punch + a 6–12 particle chip/dust burst + pitched SFX, all on that single frame. Keep every bit of it cosmetic and outside the deterministic sim.
